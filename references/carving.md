# 路线 D：雕刻已释放的旧 extent（最后手段）

雕刻（file carving）不看文件系统，直接在**原始块设备**上按文件头尾特征扫描，
把还能认出来的文件切出来。它是 A/B/C 三条路线都失败之后的兜底。

## 先想清楚：这一条什么时候才有意义

雕刻能捞回来的东西，只有一种：**盘上还留着、但文件系统已经不再指向的原始字节。**

对应到勒索场景：

| 情况 | 雕刻能不能救 | 原因 |
|---|---|---|
| `no_candidate` + 旧 extent 已释放，但物理块还没被复用 | **能** | 原件的头部字节（`%PDF-`、`PK\x03\x04`、JPEG 的 `FFD8FF`）还在盘上，能被签名扫到 |
| 旧 extent 已被后来的数据覆盖 | 不能 | 盘上已经是别的内容，签名扫不到 |
| `exact`（旧 extent 还被引用着） | 不需要 | 路线 A 已经精确拿到了，雕刻反而更差（丢失路径与时间戳） |
| `no_candidate` 但文件被整段加密（`0x24`） | 能，但只能"猜" | 雕刻出来的就是原件，可用；**但没有任何密文片段能用来比对验证**，只能靠长度和文件结构自证 |

**关键判断：卷的数据区越接近写满，旧 extent 被复用的概率越高，雕刻的命中率就越低。**
第一个案例里数据区写到 99%，推测类候选 18 个换 next 候选无一改善——同样的道理，
卷写满时雕刻多半也是白干。所以先跑 `RUN env /volume1` 看空闲空间，再决定要不要投入。

## 红线

1. **雕刻只读，但会狂读盘。** 整卷扫描是几百 GB 级的顺序读，会把 NAS 拖到很慢。
   恢复期间本来就要减少写入，雕刻和导出**不要同时跑**。
2. **输出目录必须在 NAS 之外。** 切出来的文件往往比卷上剩余空间还大。
3. **不要在数据卷上跑。** foremost/PhotoRec 都不是只读工具（PhotoRec 会写自己的状态文件），
   一旦分区选错就是在往数据卷上写。
4. **切出来的东西可能包含别人的数据。** 共享目录里其他用户的文件碎片也会被扫出来。
   只处理自己有权处置的数据，产物不要外传。

## 第 1 步：定位数据卷在块设备上的位置

群晖的 `/dev/mapper/cachedev_0` 上有多个分区（系统、交换、数据卷），数据卷不在 0 偏移。
直接对着整个 md 阵列扫会连系统分区一起扫，而且容易把分区表当成文件头。

NAS 端（root）：

```bash
python carve_scan.py --dev /dev/mapper/cachedev_0 --mount /volume1 \
    --types jpg,png,pdf,docx,xlsx,zip,sqlite --conf-out /tmp/carve.conf
```

它会做三件事：

- 读块设备的分区表（MBR / GPT 都支持）；
- 逐个分区读 Btrfs 超块，用魔数（`BTRFS_FS_MAGIC`）确认哪个分区才是数据卷——
  **自验证，不靠猜**；
- 生成 `foremost.conf` 并打印可直接执行的命令。

输出长这样：

```
  #3  起点         32768 (  32.0 KiB)  大小 4.0 MiB  <== Btrfs 卷
  Btrfs 卷 = 分区 #3，起点偏移 32768 字节，可用长度 4.0 MiB
```

把这个偏移记下来，后面所有命令都要用它。

## 第 2 步：准备雕刻工具

DSM 上默认没有 foremost / PhotoRec。三个选择，按推荐顺序：

1. **在 NAS 上装 entware**（SynoCommunity entware 包），`opkg install foremost`。
   好处是直接读块设备，不用传镜像。
2. **把块设备流导出到本机再雕**——数据量大，不推荐，但流程一样。
3. **本机 Linux / WSL 上雕**：把设备读出来传过去。Windows 自带的 `ssh.exe` 和 PowerShell
   管道会破坏二进制流，坑见 `transport.md`。

## 第 3 步：执行雕刻

DSM 的 `dd` 是 busybox，**不支持 `iflag=skip_bytes`**，只能按块取整：

```bash
# 从数据卷起点读，管道给 foremost（间接模式）
dd if=/dev/mapper/cachedev_0 bs=1M skip=32 count=3800000 | \
    foremost -c /tmp/carve.conf -o /tmp/carve_out
```

- `skip` 是 carve_scan.py 给出的起点偏移换算成 1M 块；多扫一点无妨，少扫会漏。
- `count` 是卷长度（1M 块），能限制读的总量。
- **只扫需要的类型**（`--types`）。全类型扫描会产生海量碎片且耗时数倍。
- 输出目录指向 NAS 之外的盘；空间不够就先按目录/文件类型分批。

PhotoRec 走交互式，选分区更方便：

```bash
photorec /d/mapper/cachedev_0     # 注意路径不带 /dev/
```

PhotoRec 的优势是能按文件类型过滤、且对碎片化文件的容忍度比 foremost 好；
foremost 的优势是能写自定义签名、能配 `max_size`。

**时间估算**：整卷顺序读，速度取决于盘和 NAS 的网络吞吐。第一个案例实测
NAS 侧随机读很慢——雕刻前先用 `dd if=dev of=/dev/null bs=1M count=2000` 测一下读速。

## 第 4 步：把切出来的文件对应回原件

雕刻产物只有 `jpg00042.jpg` 这种编号，**没有原路径**。用本地端的对应脚本反查：

```bash
python carve_match.py <雕刻输出目录> --enc <NAS 上的加密文件根目录> --index enc_index.json
```

它建立 `.L0CK3D` 文件的索引（读每个文件尾部 588 字节拿到模式与原始长度），
再用两种方式匹配：

- **路径 1：按原始长度**。长度对上后，在密文文件的**明文区间**上逐字节比对——
  这是硬证据。
- **路径 2：按内容反查截断前缀**。foremost 有时切不出完整文件（没找到文件尾），
  会切出一个前缀；这时反查原始长度更大的密文文件。

结果分四种，**必须分开登记**：

| 状态 | 含义 | 证据强度 |
|---|---|---|
| `confirmed` | 明文区逐字节一致，长度也一致 | **证实** |
| `confirmed_prefix` | 明文区一致，但雕刻件是原件的前缀（被截断） | 证实但不完整 |
| `confirmed_extra` | 前 N 字节证实了，尾部是雕刻带出的垃圾 | 证实（截掉尾巴即可） |
| `size_only` | 整文件加密（`0x24`）无明文可比，**只有长度相同** | **弱候选，必须人工确认** |
| `no_match` | 找不到对应密文文件 | — |

`size_only` 尤其要当心：`0x24` 模式下密文里一点明文都没有，
长度相同只能说明"可能是"，不能说明"就是"。这些文件要人工打开确认。

`--tol` 只放宽**内容已验证**那条路径（foremost 常在尾部多切出垃圾，
`--tol 1048576` 就能覆盖）。弱候选永远要求长度精确相等。

## 第 5 步：验证

按 `SKILL.md` 第 9 节（验证）执行，重点是：

- 切出来的文件能不能被正常程序打开（zip/xlsx 能解压、PDF 能打开、图片能解码）；
- `confirmed` / `confirmed_prefix` 的文件，明文区一致本身就是最强的证据；
- `size_only` 的文件**必须人工确认**，不能计入"已恢复"。

## 什么时候该放弃雕刻

- 数据区空闲空间 < 5%（旧 extent 大概率已被复用）；
- 雕刻跑了几个小时，切出来一堆碎片但几乎全是 `no_match`；
- 找不到 `no_candidate` 类的文件（那说明没什么可雕的）。

这时候把精力放回**路线 C（找其它副本）**：备份目录、备份 zip、其它用户目录、
手机和云盘，通常比雕刻的性价比高得多。

## 资源占用：雕刻是"全盘顺序读"，必须限并发

**雕刻/强签名扫描会吃满磁盘带宽。NAS 是用户的生产设备，不是专用恢复机——
不限并发会把 NAS 拖到"卡得要死"**（2026-10-31 实测教训）。

RAID1 机械盘阵列上的实测吞吐：

| 并发 | 聚合吞吐 | NAS 剩余带宽 |
|---|---|---|
| 单路 | 258 MB/s | ~100 MB/s |
| **2~4 路** | **906 MB/s（4 路）** | 有余量 |
| 20 路 | 341 MB/s（磁头互踩，反而更慢） | **几乎为 0，NAS 全线卡顿** |

**并发不是越多越好**：机械盘磁头寻道互相干扰，20 路比 4 路还慢。

执行要点：

- **用 2~4 路**，别照抄"多开几个窗口"的直觉。
- DSM 上**没有 `ionice`**，只能用 `nice -n 19` 降 CPU 优先级；IO 优先级只能靠限并发让出来。
- **定位磁盘读大户用 `/proc/<pid>/io` 的 `read_bytes` 差值**（真实磁盘读），
  不要信 `ps` 的 `%CPU`（D 状态进程 %CPU 很低却能吃满 IO）。
  本轮实测：`syncd` / `fileindexd` / `synoindexd` 读盘全为 0，**系统索引不是瓶颈，别去动它**。
- 采集进度时**不要 `cat` 大文件全文**（state 文件几个 GB 时等于每分钟读几个 GB，CPU 打满）。
  用 `awk '{last[$1]=$2} END{...}'` 一次遍历求和，且不要把原文输出到 SSH 终端。
- **扫描期间别同时跑导出/校验**，两者抢同一块盘。
- 跑之前告诉用户"这会占用磁盘带宽，NAS 会变慢"，并给出随时暂停的方法。
