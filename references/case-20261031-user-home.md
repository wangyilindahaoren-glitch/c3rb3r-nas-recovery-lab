> ⚠️ **本文件已脱敏**：人名、公司名、品牌名、共享名、NAS 地址、子卷 ID、G 值、
> 具体文件名全部替换成占位符。保留的是**路线选择依据、数字和教训**。
> 化名对照：用户A = 目标 home 所属用户；用户B/C = 其他用户；公司甲/乙/丙 = 业务主体。

> 这是 `c3rb3r-nas-recovery-lab` skill 在**同一台 NAS**上的第二次实战（第一次是另一批用户
> home 的 `.osheet` 批量恢复，见 `case-20261031-osheet-batch.md`）。本轮目标不是 `.osheet`，
> 而是一个普通用户 home 目录里的 **624 个各种格式的密文**。
> 本案例把「用户点名某个目录时怎么打」这条路完整走了一遍。

## 一、目标与结果

- 目标：`/volume1/homes/用户A`（子卷 `用户A丨个人文件`），624 个 `.L0CK3D`，1.22 GB。
- 结果（扫描完成前）：**142 个完整原件装回原目录**；140 个文件拿到明文（均值 56.9%）；
  45 个 PDF 重建后严格校验 0 问题；19 个容器救回 131 个成员；4 个表格还原（含 2810 行发票数据）。

## 二、环境

| 项 | 值 |
|---|---|

## 三、关键结论（这几条直接决定了路线选择）

1. **`survey` 全 `no_candidate` 不等于没救**。它只说明旧 extent 不再被文件树引用。
   路线 B（明文提取）和路线 D（雕刻）都还通着。本轮 140 个文件靠路线 B 救回了内容。
2. **密文尾部标记里的 `orig_len`（`footer[580:588]`，u64 LE）是最可靠的长度基准**。
   624 个文件 `size == orig_len + 588` 全部成立 → 标记自洽。
   路线 C 的匹配键用 **「文件名 + orig_len」**，比「大小差 588」更直接。
3. **这个 home 里绝大多数文件根本没被加密**：8512 个文件里只有 624 个是密文，
   其余 7888 个是明文原件（`Backup/` 627 个 + 普通目录 7246 个 + 回收站）。
4. **142 个原件全部来自 `Backup/<PC机器名>/…`**（这台电脑的备份目录），不是 7.9GB 的
   `用户A-勒索病毒源文件备份.zip` —— 那个 zip 是**加密后**的目录快照（627 个条目全是 `.L0CK3D`，
   明文条目 0 个）。
5. **`@sharesnap` 快照是"上一代目录结构"**：10-30 快照有 7227 个明文文件，但目录名和文件大小
   与当前树对不上（1300 个同名文件大小不同），是用户后来整理过的旧版本。
   只有同名同大小的才算数，按路径对照不上是正常的。
6. **密文的 mtime/ctime 都不可信**：当前树 623 个密文的 ctime 全是"当天"（整棵树被重新复制过，
   可能是 zip 解包或同步回滚），mtime 却是勒索时的 08:xx。判断加密时刻要靠 `gens`。
7. **没有勒索进程在跑**（`ls -l /proc/*/exe | grep deleted` 只有 DSM 自己的 busybox），
   内存取密钥这条路已经关闭。

PDF 重建 45/58，严格校验 0 问题；容器抢救 19 个 / 131 个成员（44 xml、30 pdf、24 rels、24 png、4 csv、3 xlsx）。

## 五、路线 C 的证实方法（本轮新写：`scripts/verify_origins.py`）

用**密文的未加密区**和候选原件逐字节比对：

- mode 0x26：明文区 `[1MiB, n)`
- mode 0x25：两段间隙
- mode 0x24：没有可比对区 → 只能标"同名同大小"

实测 142 个候选：**23 个 `proven`（逐字节一致）、119 个 `name_size_only`、0 个不一致**。
"0 个不一致"本身就是强证据 —— 说明这批同名同大小的文件确实是原件。

## 八、踩过的坑（已写进 `references/pitfalls.md`）

## 十一、三处同长度歧义的取证结论

雕刻候选按长度认领时，有 3 个尺寸对应多个目标路径。**不要凭猜，逐个取证**：

| 尺寸 | 情况 | 取证方法与结论 |
|---|---|---|
| 56119 | 同一张支出明细出现在两个目录 | 盘上有 **2 份物理副本，SHA-256 完全相同** → 两个原件本就是同一份 → 一份装两个路径 |
| 211747 | 同一份身份证复印件出现在两个目录 | 2 份物理副本**内容不同**（同一次扫描的两次成像，CreationDate 差 4 秒）→ 一一对应分配 |
| 28858 | 同一份开票明细出现在两个目录 | 盘上只有 **1 份**物理副本 → 同一份装两个路径 |

**关键判据（本轮新学）**：**同一明文 → 密文不同**（每个文件 nonce 随机）。
实测 5 组"明文区逐字节相同"的同长度密文对，密文正文有 **99% 字节不同**。
所以 0x24 文件的同长度密文对**不能**用密文判断"是不是同一份"，只能靠**多个物理副本的内容比对**。

## 十二、新路线：全盘明文索引（`scripts/plain_index.py`）

  其中 **9 个能逐字节证实**。

# 十六、第三轮（2026-11-02）：OLE2 按正文认领 + 扫描改单路

## 背景

第二轮结束时的缺口：483 个雕刻目标里 347 个（71.8%）原路径已有明文，仍缺 136 个
（pdf 100 / xlsx 12 / xls 8 / docx 5 / doc 4 / png 7）。
PDF 全盘补扫（`carve_gen_hits.py`，2 路 × 137 chunk）23:34 启动。

## 一、扫描改成单路（用户要求）

用户反馈"双路导致 NAS 加载很慢"。处理：

1. `kill` 掉第 2 个 worker（SIGTERM）；
2. 发现 `carve_gen_hits.py` 的命中文件用 **1MB 缓冲**，被杀的 worker **63924 次命中全丢**
   （`.tsv` 还是 0 字节）→ 改成**行缓冲**，并给脚本加 `--skip-file`（全局 chunk 号跳过）
   支持换并发数续扫；
3. 老的 worker 0 用 SIGINT 优雅停机（`finally` 里 close → 缓冲区落盘），
   单路 worker 以 `--workers 1` 重跑；
4. 结果：load average 从 **9.95 → 5.8**，NAS File Station 恢复流畅；单路 156-158 MB/s。

> 教训：杀扫描进程一律先 SIGINT；命中日志必须行缓冲。

## 二、`.xls`/`.doc` 按正文认领（本轮最大突破）

上一轮结论是"OLE2 长度匹配 0/6 命中，装不了"。**这个结论是错的**——`ole2_size.py`
的长度公式少算 512 字节，把真候选全排除在匹配之外。

改用 `scripts/ole2_lib.py`（新写）：

## 三之二、扫描器两个 bug（本轮踩到并修掉）

1. **命中日志丢数据**：`carve_gen_hits.py` 写命中用 1MB 缓冲，进程被 SIGTERM 杀掉时
   缓冲区里的 **63924 次命中全丢**（`.tsv` 还是 0 字节）→ 改成**行缓冲**。
2. **离线配对覆盖**：`do_match` 里 `starts[kind] = s` 是**赋值**，多 worker 的
   `starts_pdf_0.tsv` / `starts_pdf_1.tsv` 后者覆盖前者。worker1 的文件恰好是空的
   （见上一条），于是 starts 变成空集 → **配对命中 0 条**，看着像"盘上没这些 PDF"。
   改成 `starts.setdefault(kind, set()).update(s)`。
   实测：改之前扫了 22/274 个 chunk 配对 0 条 / 0 个目标长度；
   改完同一份数据立刻 **282 条 / 89 个目标长度**。
