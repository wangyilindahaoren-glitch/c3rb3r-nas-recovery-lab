# 实战踩过的坑（排查清单）

| 现象 | 原因 | 处理 |
|---|---|---|
| 用 FIEMAP 相邻 delta 重组的大视频报"moov atom not found" | 加密段跨越了一块已被完全覆盖并释放的 128MiB 原 extent，相邻 delta 推算读到了别的数据 | 改用 EXTENT_DATA 树（`c3r_btrfs.py`）区分 exact 和 infer，后者需要解码裁决 |
| csum 核对几乎全是"无记录"，自检为 0 | 用了 TREE_SEARCH V1，4KB 缓冲装不下单个 csum 项（最大约 16KB），内核返回 0 项 | 用 TREE_SEARCH_V2 配 1MB 缓冲（脚本已处理） |
| 普查时 NoCOW 文件全部被跳过 | 早期脚本见到 +C 属性就直接排除 | NoCOW 只是一个标签。子卷 lastsnap 之前的数据仍会 CoW，必须照常分析 |
| 小文件被列为"需要推测"，数量巨大 | 整文件加密时文件内没有任何旧 extent 可供外推 | 归为 no_candidate（脚本已处理），不要计入"可恢复" |
| exact 文件和"已知原件"有一个 4K 块不同 | 本地副本本身有坏块，或是另一个版本 | 用 csum 判定：NAS 侧逐块一致，说明恢复结果才是对的 |
| exact 文件 ffmpeg 解码报错（cu_qp_delta、slice_qp、SEI truncated、AC3 incomplete frame、PNG truncated） | 原文件本身就有这些问题 | csum 一致即算成功；NoCOW 共享无 csum 时注明"原文件可能固有问题" |
| 大量"non monotonically increasing dts to muxer"导致误判失败 | ffmpeg 输出到 null muxer 时，iPhone 可变帧率视频会触发时间戳警告 | 过滤这类良性警告（`c3r_local.py` 已处理），并去掉随之出现的 "Last message repeated" |
| HEIC 全部"无法识别" | 缺少 pillow-heif | 安装 pillow-heif；没有它时应记为 not_checked，而不是失败 |
| 传输停在约 100MB | paramiko 窗口或流控问题 | 改用原生 OpenSSH |
| ssh 报 Connection reset | 命令行参数过长（内嵌了 base64 列表） | 用 stdin 传作业（`mkjob.py`） |
| 远端报 `set: -: invalid option` | 在 Windows 上生成的脚本是 CRLF 换行 | 按字节写出 LF |
| 目标盘写入极慢、磁盘占用率显示 1000% | 近满的 SATA SSD（SLC 缓存耗尽） | 换盘；写入前先测速 |
| 验证阶段 E 盘几乎没有写入、NAS 闲置 | 导出和单线程验证串行执行 | 拆开，验证多进程并行 |
| ssh "Permission denied" 后导出为空 | 自动化时忘了传密码环境变量 | 每次检查 `.err` 输出和 tar 是否为空，不要只看退出码 |
| `25142000` 等未知模式 | 百分比参数不是 0x0a，公式未知 | 改写范围由新 extent 推出；若根本没有新 extent，多为 NoCOW 原地覆盖 |
| 选错 G | 采样只覆盖了单个目录 | 多个共享一起采样；确认 G 以下存在代数空档；边界自校验会暴露错误 |
| 雕刻扫出几百个命中，"一个都不匹配" | **把逻辑地址当物理偏移读了**（`btrfs` 给的 extent 地址是逻辑地址） | 逻辑→物理必须过 chunk 表换算；开扫前先拿一个已知地址**校准**（见 `references/carve-osheet.md` 第 3 节） |
| 认领时全部判定失败 | 把容器尾部标记里的 u32 当成文件长度 | 那个 u32 是**尾部段自身长度（=11）**；文件长度 = (尾部标记起点 − 4) + 该 u32 |
| 认领到一堆长度不对的容器，误判"原件不在盘上" | 只细看了邻近命中的**前几个**就下结论 | **必须批量认领**全部命中（`carve_osheet_identify.py` 一次读全部日志）；本轮第 6 个邻近命中恰好就是原版 |
| 认领到的容器头部是 `schema` 长度 2 | 那是**旧版 WPS 格式**，不是目标文件 | `schema` 长度 3 = 现代版（现代头 39 字节固定，见 `references/carve-osheet.md`） |
| 在元数据区反查旧叶子块，卡在叶内 item 布局上 | 叶内 item 头阵列的真实布局试了三版都没钉死 | **别在元数据区硬啃**——直接扫数据区（快 10 倍且稳）；EXTENT_DATA 的 key type 是 **108** 不是 168，数据体 53 字节 |
| 恢复目录名写错（"加贿恢复_20261030"） | 中文 unicode 转义抄错（`勒索` = `\u52d2\u7d22`） | 不要硬编码中文目录名；**按目录结构识别**（如找含 `恢复说明.txt` 的那个目录），或先在本地 `encode('unicode_escape')` 打印一遍再抄 |
| 雕刻出的 `.osheet` 看着能解析，WPS 仍打不开 | 用宽松解析器判定 | 交付前必须 `osheet_strict.py` 严格复核；本轮尾部 u32 误读就是靠严格解析暴露的 |
| 认领脚本只认领了一半，该认的没认 | `--len 48250 19559` 只吃掉了第一个值，第二个数字被当成日志文件名 | 已改 argparse：`--len N [N...] --label A [A...] --log <日志...>`，**日志一律用 `--log` 指定** |
| 推测类压缩包大量 CRC 失败，换 next 候选也不行 | 释放的原 extent 已被复用（数据区接近写满时很常见） | 接受现实：抢救未受影响的成员；不要反复猜参数 |
| 压缩包测试被误判为"分卷"等 | 按输出文字关键词分类时，路径里的 `/volume1/` 命中了 "volume" | 按 `Total errors: N` 和明确的错误信息分类 |
| `inline` 状态 | 2KB 左右的小文件内联存放在元数据里，元数据也 CoW，旧的叶子节点多半已被复用 | 一般放弃；可以考虑 btrfs-find-root 加旧树根，属于专家级个案 |
| `compressed` 状态 | 共享启用了透明压缩，extent 内是压缩数据 | 需要按 extent 读出整块再解压（zlib、lzo、zstd），本工具未实现 |
| 输出目录里有 `homes`、`volume1` 等不同前缀 | 不同版本脚本的成员名基准不同 | 本工具统一以 `/` 为基准，成员名形如 `volume1/...` |
| 普查出现大量 `no_candidate`，看起来全完了 | 勒索程序把整个文件重写成了新 extent，旧 extent 已释放回收 | **不等于没救**：新 extent 里未加密的区间仍是原始明文，改走路线 B（见 `plain-extract.md`） |
| 自己手写的 0x25 公式算出负的 gap | 百分比算错。正确是 `w = 4 * (n // 100)`、`gap = (n - 3w) // 2` | 直接复用 `c3r_btrfs.py` 的 `formula_ranges()`，不要另写；不确定时用 `probe_modes.py` 反推 |
| 明文片段拼起来后 zip 报 BadZipFile | 拼接丢掉了密文区，成员偏移全乱 | 密文区填 0、保持原文件总长和偏移，再交给 `salvage_zip.py` 逐成员抢救 |
| `salvage_zip.py` 救回成员数为 0 | 直接从填充后的文件读，数据落在密文区 | 必须从**原始 .L0CK3D 文件**读，用中央目录偏移定位，CRC 校验 |
| 用同名文件当原件 | `1.png` 这类通用名在别处可能是完全不同的文件 | 必须逐字节比对；大小差 588 字节只是线索，不是证据 |
| `scp` 传中文名+空格的文件报 "protocol error: filename does not match" | Windows OpenSSH scp 的文件名编码问题 | 改用 tar 流传输：`tarout.py` 打包成流 piped 给远端 `tar -x` |
| 用 `cpio` 复制 Windows 路径 | `cpio` 把反斜杠当普通字符，产生了 `xxx\D:\...` 这样的垃圾条目 | 用 Python 的 `os.walk` + `shutil.copy2`，或 tar 流 |
| NAS 端 python 脚本用 heredoc 传时被吞 | 嵌套 heredoc（sh 里再套 `cat <<EOF`）经多层 ssh 转发会截断 | 脚本用 base64 传：`echo '<b64>' \| base64 -d > /tmp/x.py`；密码行走 stdin 第一行 |
| Windows 目标机的 ssh.exe 卡在 KEX | 该机 sshd/安全软件异常（本例 360 卫士） | 改用**反向推送**：NAS 用自带的 Linux 版 ssh 主动连目标机；或用原始 socket 探测确认网络正常 |
| Windows 目标机收二进制流时数据被改写 | 用了 `more`（会做分页文本处理）或 PowerShell 管道 | 让 Python 直接读 `sys.stdin.buffer`；cmd 的 `>` 重定向是二进制安全的 |
| 目标机 sshd 起的会话写不了目录 | 权限/ACL 与交互式会话不同 | 先在交互式会话里 `python -c "open(...,'wb')"` 测一下；必要时调 ACL |
| 密钥认证放到 `~/.ssh/authorized_keys` 无效 | Windows 上 administrators 组成员读的是 `__PROGRAMDATA__/ssh/administrators_authorized_keys` | 写到该文件并 `icacls` 设为 Administrators + SYSTEM 完全控制 |
| 雕刻切出一大堆碎片，几乎全是 `no_match` | 旧 extent 已被后来的数据复用，数据区接近写满 | 卷空闲空间 < 5% 就别雕了，把精力放回路线 C（找副本） |
| 雕刻把系统分区也扫了一遍，还切出"分区表文件" | 直接对整个 md 阵列扫，数据卷不在 0 偏移 | 先跑 `carve_scan.py` 读分区表并用 Btrfs 超块魔数定位数据卷起点 |
| `dd iflag=skip_bytes` 在 NAS 上报不支持 | DSM 的 `dd` 是 busybox | 按块取整：`bs=1M skip=<起点/1M>`，多扫一点无妨，少扫会漏 |
| PhotoRec 跑完在数据卷上多出几个文件 | PhotoRec 不是只读工具，会写自己的状态文件和恢复记录 | 在别的机器上跑，或把输出目录指到卷外 |
| foremost 切出的文件尾部带一大截垃圾 | 找不到文件尾时按 `max_size` 一直写下去 | 用 `carve_match.py --tol 1048576` 匹配，尾部截掉即可 |
| 雕刻输出把目标盘撑爆 | 碎片数量可能是卷容量的数倍 | 只扫需要的文件类型（`--types`），分批出，结果落 NAS 之外 |
| 把 `size_only` 的雕刻候选当成"已恢复"报上去 | `0x24` 整文件加密模式里一点明文都没有，长度相同只能说明"可能是" | 必须人工打开确认，单独登记，不能与 confirmed 混在一起 |
| 雕刻产物里混着别的用户的文件碎片 | 扫描的是整块设备，共享目录里所有人的数据都会命中 | 只处理自己有权处置的数据，产物不外传 |
| 用户说"恢复的文件一个都打不开" | 往原目录写的是"明文提取"产物：密文区填 0，文件头是 0，zipfile 直接 BadZipFile | 写回原位前必须做结构验证（见 `references/osheet.md` 第 3 节三关），只写"验证通过"的原件 |
| 同一批文件在原目录出现两份（原名 + `_部分修复`），内容一样 | 先后两轮用了不同判定标准 | 统一规则：全好→原名；部分→带后缀；同一原件只留一份 |
| `.osheet` 用 zipfile/openpyxl 读不了，报格式错误 | 它是 WPS OSheet 自有容器，magic `78 00 00 00`，条目链里压缩条目还嵌着后续条目 | 用 `scripts/osheet_parse.py`；条目要递归展开，不能只扫一层 |
| 逐字节盲扫 zlib 找 OSheet 条目，22MB 文件跑了几十分钟没完 | 一个文件里有几百个 zlib 头，每个都要试解压 | 以条目名（`text/xxx`）为锚点定点试，位置偏移量只有几十字节 |
| OSheet 修复件解出的分片数比 index 少 | 被加密的那一段（`0x26` 是前 1MiB）只能靠路线 A 推测，推错了就解不出 | 标"部分修复"，把已解出的分片导成 CSV 交付，别硬说已恢复 |
| 路线 A 的候选在明文区有几千字节对不上 | 候选是外推出来的，明文区也可能有误差 | 用密文的明文区原字节覆盖回去（`osheet_fix.py` 的合并修法），明文区因此变精确 |
| 用宽松解析器判定"文件没问题"，用户却报"无效文件格式" | 宽松解析只认名字锚点，字段错位一字节它照样读得出条目 | 交付前必须用**严格**解析器（`osheet_strict.py`）复核；本次 29 个坏件在宽松解析下全部"通过" |
| `.osheet` 重建后 WPS 还是打不开 | 长度字段错位：合并修法只保证内容准，头部/X/len 仍可能错 | 用 `osheet_rebuild.py` 只重写 X/len、头部用正常文件当模板；重建器先拿正常文件往返验证 |
| 群晖上恢复出来的文件，admin 在 File Station 里读不到 | root 写的文件是 "It's Linux mode"，没有 Synology ACL | `synoacltool -copy <原始文件> <目标文件>`；**顺序：先 chown/chmod，最后复制 ACL**（chmod 会把 ACL 抹掉） |
| 恢复目录建出来是 root 的，admin 连目录都列不出来 | 同上，目录也要 ACL | 目录用**目录**当模板复制（文件模板复制到目录上不生效） |
| `synoacltool -copy` 报成功但文件仍是 "It's Linux mode" | 后面又执行了一次 chmod，把 ACL 冲掉了 | chmod 永远放在复制 ACL 之前 |
| 重建出来的 PDF 双击打不开 | trailer 里把 `/Root` 写死成 `1 0 R`，而原文的 Catalog 不是对象 1、或根本不在明文区 → **没有 Catalog 的 PDF 阅读器一律拒绝打开** | 扫描 `/Type /Catalog` 定位；没有就自己造 Catalog + `/Type /Pages` 页树，并给页面对象补 `/Parent`（`scripts/pdf_rebuild.py`） |
| PDF "看着正常"其实坏了 | 只查了 `%PDF-` 头和 `%%EOF` 就判定"能打开" | 还要查 `startxref` 指向的 xref 表、xref 里每条偏移量是否真的指向对应对象、页面的 `/Contents` 是否在文件里 |
| 重建 PDF 时漏掉大半页面 | PDF 1.5+ 把大量对象放在 `/Type /ObjStm` 对象流里，没解压就找不到 | 扫对象时顺带 zlib 解压 ObjStm，把里面的对象也放出来 |
| 雕刻扫描长时间"在跑"但进度不动，state 文件涨到几个 GB | `carve_worker.py` 的步进写成 `pos += want - OVERLAP`：chunk 剩余不足 `OVERLAP` 字节时 `want == OVERLAP`，步进变成 0，worker 陷入死循环，每轮只读 64 字节、反复往 state 文件追加同一行 | 步进必须严格为正：`step = (want - OVERLAP) if want > OVERLAP else want`，并加 `if step <= 0: break` 兜底。**判据**：压缩 state 后每个 shard 只剩 1 行 = 全卡在第一个 chunk；`rchar` 涨得慢而 CPU 只有 13% = 死循环不是 IO 瓶颈 |
| 状态采集脚本把 NAS CPU 吃满（ssh 进程占 99%） | `status.sh` 每 60 秒 `cat state/shard*.done \| grep -c` 全文，state 文件有几个 GB 时等于每分钟把几个 GB 读一遍 | state 文件异常膨胀要先修 worker 再重扫；采集脚本改用 `awk '{last[$1]=$2} END{...}'` 一次遍历求和，且不要 `cat` 原文输出到 SSH（会撑爆终端并被杀） |
| 雕刻扫描把 NAS 拖到"卡得要死" | 扫描是全盘顺序读，20 路并发把 RAID1 阵列读到 341 MB/s，NAS 只剩 ~30 MB/s | 机械盘并发过高会磁头互踩：**实测单路 258 MB/s、4 路 906 MB/s、20 路 341 MB/s → 用 2~4 路**；DSM 无 `ionice`，只能 `nice -n 19` + 限并发让出 IO |
| 怀疑"群晖系统索引在扫盘"导致卡顿 | **实测不是**：`syncd` / `fileindexd` / `synoindexd` / `synoindexscand` 的 `read_bytes` 全为 0，索引服务空闲 | 定位磁盘读大户要用 `/proc/<pid>/io` 的 `read_bytes` 差值（真实磁盘读），**不要信 `ps` 的 %CPU**——D 状态进程 %CPU 很低却能吃满 IO。本轮 98% 的读盘来自雕刻 worker |
| Drive 重建的 `.osheet` 长度比勒索标记的 `orig_len` 大 | **旧版** `rebuild_from_drive.py` 会多追加一段尾段、并把附件数据区吞进末条目 | **长度对不上 ≠ 重建失败**。`orig_len` 只用来校验雕刻出的原件；重建件的长度不能当判据，改用 `osheet_strict.py` + 全量逐格比对。**注意：改用 `rebuild_exact.py`（字节级重建）后，长度就重新变成有效判据了 —— 重建长度必须 == orig_len**，见 `references/synology-drive.md` 第 9 节 |
| 雕刻出的原件**没有** `text/attachment` 条目，就断定"原文件没图片" | 附件条目正好落在勒索加密区时被抹掉了 | 看 `drawing` 字段和条目链之外的数据区；**附件元数据在、图片二进制不在**才是常见情况，要如实说"图片没救回来" |
| `scp` 传文件报 `subsystem request failed on channel 0` | DSM 的 SSH 没开 SFTP 子系统 | 用 `ssh` + `sudo cat` 管道下载：密码走 `SSH_ASKPASS`，文件内容从 stdin 灌 |
| Windows 上 `python` 命令退出码 49、什么都不输出 | `python` 指向 Microsoft Store 的占位 stub（`AppData/Local/Microsoft/WindowsApps/python`） | 用真实解释器 `AppData/Local/Programs/Python/Python38/python.exe` |
| NAS 上写 `bc` 算速率报 `command not found` | DSM 的 busybox 没装 bc | 用 python 计时（`os.pread` 循环 + `time.time()`），或直接读 `/proc/diskstats` 两次采样求差 |
| 写清理脚本时 `for f in "$DIR"/* .osheet; do rm -f "$f"; done` 把**整个目录清空了** | `"$DIR"/*` 里的 `*` **在引号外**，`for` 把它当成多个词：第一个词展开成目录下所有文件，后面跟字面量 `.osheet`，于是 `rm -f "$f"` 挨个删光 | 删文件一律用 `find <目录> -maxdepth 1 -type f -name '*.osheet' -exec rm -f {} \;`；或用 `scripts/tidy_delivery.py`（默认预览）。**动手前先 `--dry` 看清清单** |
| 判重时把 `原名.osheet` 和 `原名.osheet.L0CK3D` 归到同一组，密文被当成"重复"删掉 | 密文只是文件名的后缀，扩展名解析没先剥掉 `.L0CK3D` | **密文单独分组**，绝不能和同名恢复件混在一起判重（反过来也会把恢复件当重复删掉） |

## 内存路线常见误区

- "没重启就一定能找到密钥"：不对。关键是**加密进程是否还活着**。进程退出后，它的内存页很快就会被回收复用。
- 只拿内存中的 ChaCha 状态对少数几个已知文件做试解：覆盖面不够。要对全部加密文件的开头字节试解，才能下结论。
- 忽略磁盘 swap：群晖除了 zram，还有 md1 交换分区，也应该扫描（通常为空）。

## 2026-11-03 某团队共享（.osheet 字节级重建）新增的坑
