## 雕刻扫描实测数据

- 卷：群晖 `/dev/mapper/cachedev_0`（`/volume1`），底层 md2 = RAID1（两块 16TB 机械盘）
- DATA chunk：278 个，逻辑总量 **2917.4 GB**
- 单 chunk 长度 10 GiB / 1 GiB 两种
- 扫描进度：**2917.4 GB / 2917.4 GB = 100%**，279 个 chunk 全扫完，命中 16009 次，去重后 **14270 个容器地址**
- 吞吐：单路 258 MB/s，4 路 906 MB/s，20 路反而 341 MB/s（磁头互踩）
- **认领判据**：雕刻出的容器长度 == orig_len → 精确命中（`claim_fast.py` 已在内部用严格解析复核）

## 扫完即可按需恢复（本次实测验证）

扫描日志（`logs/w*.log`）就是一份**全盘 `.osheet` 容器位置索引**：4316 条命中、去重 3840 个地址。
认领只从日志取地址 + 随机读块设备几百字节，**秒级，不重新扫盘**。

在扫描只跑到 23.6% 时，直接从已有日志认领出了一个**原计划之外**的文件：

```
某年度采购记录.osheet   orig_len 177020（从密文尾部 footer[580:588] 读出）
  严格解析 OK：条目 10，分片 2，工作表「客户A」(270行) / 「出纳」(373行)
  列：时间 | 金额 | 转账路径 | 交易内容 | 备注 | 快递单号 | 是否签收
  转 xlsx 后回读校验 592/592 一致
```

**原始长度不用翻勒索信——直接读目标密文尾部 588 字节的 `footer[580:588]`（u64 LE）即可。**

一次命令（`scripts/recover_one.py`）：

```bash
python3 recover_one.py "<密文路径>" --xlsx
```

限制：只覆盖扫描签名匹配的类型（当前仅 `.osheet`）；旧 extent 可能被覆盖，**扫完越早认领越安全**；
未扫到的区间捞不到。

## 交付整理（本次收尾）

`tidy_delivery.py` 整理成"每个文档一份 .osheet + 一份 .xlsx"，密文 0、中间件 0。
最终 12 个文件的 SHA-256 与本地记录逐一吻合。

## 恢复顺序（下次照做）

1. Drive 重建（分钟级）→ 立刻转 xlsx + **全量**逐格校验 → 先交付
2. 雕刻（小时级，2~4 路并发）→ 认领精确原件 → 替换重建件
3. 收尾清理：删密文 + 多余副本，只留用户要的文件（`tidy_delivery.py`）
4. 之后想恢复别的文件 → `recover_one.py` 按需认领，**不用重新扫**

## 这一轮最重要的三个突破

### 1. Drive 重建可以做到逐字节

摸清容器格式后（见 `synology-drive.md` 第 9 节），`rebuild_exact.py` 重建的容器
与雕刻出的**字节级精确原件** SHA-256 相同。批量实测 **21 个两路都有的文件里
19 个逐字节一致**（另 2 个是 Drive 存了更新版本，已查清）。

> 这一步把 Drive 重建从"拼个大概"升级成"可证精确"，直接解决了上一轮
> `价格调整记录表` 丢 4 张表的老问题。

### 2. 两条路互为证明

雕刻能捞到的不多，但它给出的是**盘上原始字节**——正好当 Drive 重建法的 ground truth。
反过来，Drive 重建能覆盖雕刻捞不到的。两路合起来 74 个里救回 58 个。

### 3. 长度匹配要加防线

按「重建长度 == orig_len」匹配 Drive 仓库，**会撞车**（实测 1 例对到了别的文档）。
防线：有雕刻原件时用它的 `id` 字段做精确键；没有时加同目录 uid 一致性过滤。
详见 `batch-osheet-recovery.md` 第 2.2 节。

## 第三轮：雕刻索引按 `id` 反查（把剩下 16 个里的 7 个救回来了）

前两轮都是「按长度盲猜」，第三轮换了索引维度，命中率从 0 拉满。

**原理**：`.osheet` 容器头的 `id` 字段 = Drive 仓库目录名，固定偏移。
把雕刻索引里每个命中地址的 `id` 提出来（读 512 字节即可），
就能定位「这个文档在盘上还有哪些历史版本」，再按长度筛。

实测数据：

- 索引 14270 个地址 → 6861 个可解析容器 → 68 个不同 id
- 其中一个文档，盘上留了 **346 个历史版本**（4316 ~ 54196325 字节）
- 全量算长度（nice 19 单路，约 25 分钟）对 15 个未救回目标 → **7 个精确命中**

新增的坑：

- **`.osheet` 有两种形态**：Drive 重建件是「不压缩形态」(tag=0x02)，
  用户自己在 WPS 保存的原件是「压缩形态」(tag=0x05、`@C_` 前缀、schema 值 3 字节)。
  **勒索时被加密的原件两种都可能是** → 长度匹配必须两种都算（只算不压缩形态会漏掉全部 WPS 原生件）。
- **同一份业务文档可能有多个 Drive docid**：同一张表在不同账号下各有一个仓库，
  内容不同（欠款明细 509 行 vs 450 行）。**只按 uid 猜会漏一半**，必须按 id 全量扫。
- **群晖回收站和 `@sharesnap` 是路线 C 的金矿**：团队共享回收站里躺着 3 份勒索前明文原件。
- **勒索时的 orig_len 与「最后一次 Drive 同步」的版本可能差几十字节**：说明用户本地改过但没同步。
  这种情况下最好结果是 Drive/回收站版本，交付时要说清差在哪。

最终 **74 个 `.osheet` 救回 65 个（88%）**。
