## 起因

有人问："ext4 支持吗？"

结论：ext4 **没有写时复制**，路线 A（从 Btrfs 旧 extent 逐字节还原）
**原理上不成立** —— 勒索程序原地改写就把旧内容物理覆盖了。
但 ext4 有自己的路，合计能救回相当一部分。

## 这一轮做了什么

| 产出 | 说明 |
|---|---|
| `references/ext4.md` | ext4 完整路线：原理、执行序、每步命令、按 mode 的现实预期、话术、红线 |
| `scripts/ext4_probe.py` | 读 ext4 超块（块大小 / inode 数 / 特性位 / 日志 inode）、`debugfs lsdel` 列已删 inode、`--dump-journal` 导出 jbd2 日志镜像 |
| `scripts/jrn_match.py` | 用密文的**明文区当指纹**在日志镜像里定位旧内容，按「文件偏移 → 日志偏移」映射把被覆盖的原始字节取回来拼成候选原件 + 结构校验 |
| `carve_scan.py --fs ext4` | 按 ext4 魔数 `0xEF53`（分区起点 + 0x438）自验证定位分区，不靠猜 |
| `carve_gen*.py --dev / --range` | ext4 没有 DATA chunk 概念，扫描器改按字节范围整段扫；日志镜像这类普通文件也能直接喂进去 |

## 关键设计：为什么 jbd2 日志里有旧内容

ext4 默认开日志，挂载选项默认 `data=ordered`：
**文件的数据块在元数据事务提交之前会先写进日志，日志里保存的是这些块的旧内容。**
勒索程序改写文件必然伴随一次元数据事务（大小变了、mtime 变了），
于是**被覆盖前的旧内容被写进了日志**。

定位办法：密文文件里有两段 —— **明文区**（没被加密，字节原样）和
**加密区**（现在是密文）。用明文区当 96 字节指纹在日志里搜，
**多个探针指向同一个「文件偏移 → 日志偏移」映射 `delta` 时才认**；
加密区在日志里对应的位置，放的就是旧的原始字节。
拼起来 = 候选原件，再做魔数与结构校验。

**时效性**：日志只保留最近的事务（默认 4MB，最大 64MB），
**卷上每写一次东西就可能把旧内容挤出去** → 导日志要放在所有动作的**最前面**。

## 自检结果（合成样本，28 项断言全过）

- **ext4 超块定位**：分区起点处认出魔数；非 ext4 位置不误报；
  分区表里认对分区；**不把 ext4 误认成 btrfs**
- **`jrn_match`**：0x26 明文区从 1MiB 开始；多个探针定位到同一 delta（`multi`）；
  魔数识别为 pdf；**文件头来自日志**（独立证据）；结构校验通过；
  **拼出来的候选件与原始文件逐字节相同**；
  日志里没有时**如实报 `not_in_journal`**，不硬凑
- **`carve_scan --fs ext4` 全流程**：认出 ext4 卷、起点偏移打印正确、
  自动打印 ext4 专用扫描命令与红线
- **`carve_gen_hits --range`**：按字节范围扫到 pdf 开头偏移、
  日志里记下扫描范围、离线配对按目标长度命中

## 顺手修掉的一个静默失败

两个扫描器的读取失败被 `except Exception: pass` 吞掉 →
扫描"跑完了"却 **0 命中**，看着像"盘上没这文件"。
（Windows 上 `os.pread` 不存在，正好复现了这个坑。）

现在会把错误打出来。

**教训**：扫描类脚本的读失败**必须显式报出来**。
"扫完了 0 命中"和"盘上没这文件"是两件事，混起来会浪费好几小时。

## 没验证的部分（**别当成已验证**）

- 没在真实 ext4 卷上跑过 `ext4_probe.py`：超块字段偏移、`debugfs` 输出格式按文档写的
- **jbd2 日志的实际留存行为没实测**：不同内核、`data=writeback` 挂载、
  日志大小配置都会影响旧数据是否进日志
- `jrn_match` 的映射在日志跨多个事务时，可能只在一段区间成立
- `carve_install.py` 的装回流程没在 ext4 上端到端跑过（Btrfs 那边是跑过的）

## 下一次在真机上用，按这个顺序

1. 先 `ext4_probe.py` 看超块字段和日志块数对不对
2. **立刻** `--dump-journal` 导出日志镜像（别拖，卷上每写一次都在挤掉旧内容）
3. 先拿**一个已知原件**的密文试 `jrn_match`，看 `delta` 与 `magic_from_journal`
4. 再批量跑，**最后**才上雕刻（几小时，且可能白干）
