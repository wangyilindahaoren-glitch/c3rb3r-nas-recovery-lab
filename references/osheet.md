# WPS OSheet（.osheet）表格的恢复与修复

**动手前先读这一篇。** 国内中小企业里大量表格用 `.osheet`（WPS OSheet 容器），
它不是 zip、不是 OLE2，通用工具（zipfile / openpyxl / PIL）全都读不了。
用户拿到恢复结果第一反应就是"双击打不开""显示无效文件格式"，这一篇就是解决这个问题的。

## 1. 容器格式（实测，已用正常文件反推确认）

```
文件 := magic(4) + 头部TLV* + 条目* + 尾部段
magic := 78 00 00 00
头部 := [u8 tag][key\0][值]
        tag=0x12 → 值长 u32（schema，3 字节）
        tag=0x08 → 值长 u8（enc，空值）
        tag=0x02 → 值长 u32（id / ver，字符串带结尾 NUL）
        字段之间有 0x00 分隔字节
条目 := [u32 X][u8 tag][name\0][u32 len][数据(len 字节)][尾随原始字节]
        tag=0x05 → len 之后多一个 0x00，然后是 zlib 流（自带结束符）
        tag=0x02 → len 之后直接是原始数据（不压缩）
        X = 从 X 字段本身到本条目结束的总字节数（即"到下一个条目的距离"）
尾部 := [u32 总长][u8 0x08]["end\0"][值]
```

条目名实测有 `@C_` 前缀（压缩型）或没有（不压缩型）：

| 条目 | 内容 |
|---|---|
| `text/comment` `text/define` `text/file` `text/locale` | 批注、定义、附属文件等，多为 `[]` `{}` |
| `text/index` | 表格索引 JSON：`{"gcVer":3120,"maxIndex":12,"order":["sh_2","sh_1",...],"sheets":{...}}` |
| `text/sh_N` | 第 N 个分片 JSON：`{"cfs":[...],"colCount":30,"rowCount":1125,"rows":{行号:{"h":行高}},"cols":{列号:{"w":列宽}},"cells":{行号:{列号:单元格}},"hyperlinks":[...],"mergeCells":[...]}` |
| `text/style` `text/pivotCaches` `text/pivotTables` `text/attachment` `text/metatext` | 样式、透视表、附件等 |

**单元格数据在分片的 `cells` 里**：`cells[行号][列号] = {"v": 值, "s": 样式, ...}`。
`rows`/`cols` 只是行高列宽，没有值。值一般是字符串/数字，公式在 `f` 字段。

### 定位条目边界的办法（不要盲扫）

- 条目名是 ASCII，用 `text/...`、`@C_...` 当锚点；
- 压缩数据的真实结束位置用 **zlib 自终止**确定（`zlib.decompressobj()` 的 `eof` + `unused_data`），
  不要信文件里的 len 字段——**被勒索破坏的恰恰就是这些长度字段**；
- 下一个条目的起点 = 下一个名字锚点往前 5 字节（X 占 4、tag 占 1）。

## 2. 两个必备工具

| 文件 | 作用 |
|---|---|
| `scripts/osheet_strict.py` | **严格**解析器：头部 TLV、条目链、尾部段全部按文法走，任何一处不自洽就抛错。**交付前必须用它复核** |
| `scripts/osheet_rebuild.py` | **容器重建器**：只重写 X 与 len 两个字段，其余字节逐字节照抄；头部用正常文件作模板 |
| `scripts/osheet_fix.py` | 明文区 + 路线A 候选合并、抽 cells 导 CSV（见第 4 节） |
| `scripts/osheet_parse.py` | 宽松解析器：能列出条目和分片，用于探索，**不能用来判断文件是否完好** |

```bash
# 严格复核（通过 = 容器结构自洽）
python3 osheet_strict.py 文件.osheet

# 重建（模板要选一个结构正常、没被加密的 .osheet）
python3 osheet_rebuild.py 正常模板.osheet 待修文件.osheet 输出.osheet
python3 osheet_strict.py 输出.osheet     # 复核
```

**重建器必须先做往返验证**：拿正常模板自己跑一遍重建，输出应当与原件**逐字节完全一致**。
不一致就说明文法理解错了，不能拿去修别的文件。

## 3. 关键手法：密文明文区 + 路线 A 候选 = 修复件

路线 A 导出的候选（`.__prev__.osheet`）来自 Btrfs 旧 extent，
**被勒索覆盖的那一段是推测值**，其它区间是真的原文。
路线 B 又能给出密文里未被加密的那部分（原文，但密文区被填了 0）。
两者拼起来：

```
修复件 = 密文的明文区间（逐字节原文） + 候选的被加密区间（推测值）
```

这样明文区是**逐字节精确**的，容器结构也能自洽 → WPS 能打开。

`scripts/osheet_fix.py` 做这件事（NAS 端，root，Python 3.6+ 标准库）：

```bash
python3 osheet_fix.py            # 只体检并导出 CSV，不写原目录
python3 osheet_fix.py --apply    # 体检通过的文件放回原路径
```

## 4. 修复件还会"结构错位"，要再重建一次

上面这一步只保证**内容**对，不保证**长度字段**对。
路线 A 推测出来的头部可能错一两个字节（实测 `schema` 字段的长度被推成 2，正常是 3），
于是头部整体错位一字节，WPS 解析头部直接失败 → **"无效文件格式"**。

所以流程是：

```
路线A候选 ──合并修法──> 修复件（内容准）──容器重建──> 结构自洽的 .osheet
                        （头部/长度字段仍可能错）      （严格复核通过）
```

实测效果（同一批文件）：

| 文件 | 重建前 | 重建后 |
|---|---|---|
| 26年售后记录表.osheet | 头部错位，WPS 打不开 | 25 条目 / 15 分片全解 |
| 开票登记表.osheet | 11/12 分片可解析 | **12/12** |
| 绩效考核表.osheet | 1/10 分片可解析 | **10/10** |
| 产品问题汇总.osheet | 0/1 分片可解析 | **1/1** |

## 5. 验证协议（照做，不要跳）

一个文件能不能说"已恢复"，要过四关：

1. **明文区逐字节一致**（硬证据）：读密文尾部 588 字节标记拿到 mode
   （`0x24` 整文件 / `0x25` 分段 / `0x26` 前缀 1MiB），
   算出明文区间，把候选/修复件在这些区间与密文逐字节比。全等 → 确实是这个文件的原件。
   `0x24` 没有明文可比，只能按结构判定，单独标注。
2. **容器结构完整**：`osheet_strict.py` 严格复核通过（头部、条目链、尾部段全部自洽）。
3. **分片全解**：每个 `text/sh_N` 都能解出含 `cells` 的 JSON。
4. **业务数据抽样**：抽一行表头和一行数据，确认是真业务内容（不是空表、不是乱码）。

第 2 关最容易被"善意"跳过：宽松解析器能列出条目和分片，
**但坏文件的字段错位它照样能读出来**。交付前只用宽松解析器 = 把坏文件发给用户。

## 6. 放回原目录的规矩

- **只新增，绝不覆盖**。目标已存在就跳过；密文 `.L0CK3D` 一个都不能删、不能动。
- 文件名规则：
  - 结构完好 → 用**原名**（用户双击就能开）；
  - 部分修复 → `原名_部分修复.<ext>`；
  - 重建的 xlsx → `原名_重建.xlsx`；
  - 路线 A 的推测候选 → `原名.__prev__.<ext>`（在恢复目录里）或 `原名_推测恢复.<ext>`（放原位时）。
- 每个文件都要有台账（JSON），写清：来源、字节数、SHA-256、验证方式（`sha_ok` / `confirmed` / `structure_ok` / `unverified`）。
- 写完立刻回读校验，别信"写成功"的返回值。

## 7. 群晖上的权限（另一个坑，会表现成"打不开"）

root 写出来的文件和目录**没有 Synology ACL**，`synoacltool -get` 报
`It's Linux mode`。后果：以 admin 身份在 File Station 里看不到、读不了这些文件，
用户会以为文件坏了。原始文件（如 `用户A.zip`）是有 ACL 的。

修法：

```bash
# 目录要用目录当模板，文件用文件当模板
synoacltool -copy <原始密文或原文件> <目标文件>
synoacltool -copy <home目录>        <恢复目录>
```

**顺序很重要**：先 `chown`/`chmod`，**最后**再复制 ACL ——
`chmod` 会把 ACL 打回 "It's Linux mode"。

模板选取：同一个用户 home 下的原始 `.L0CK3D` 文件（有 ACL 的那份）；
找不到就用 home 根目录里任意带 ACL 的文件。

属主也要改回该用户（`os.chown` 到 home 的 uid/gid），否则用户在 SMB 里改不动。

### 两个把人绕进去的细节（2026-10-30 实测）

1. **"已经有 ACL 就不动"这个判断会漏掉 chown。**
   DSM 的 home 目录带默认 ACL，新建的 xlsx 一落地就**继承**了一份 ACL，
   `synoacltool -get` 于是显示"有 ACL" —— 如果照着这个判断跳过，
   `chown` 也一起跳过了，属主就留在 root，用户在 SMB 里改不动。
   **对自己刚放上去的文件：无条件 chown → chmod → 复制 ACL。**
   （只对自己新建的东西这么做，别去动用户自己的原始文件。）

2. **不是每个 home 的默认 ACL 都带 administrators 条目。**
   实测 `用户A` 的原始文件 ACL 里有
   `group:administrators:allow:rwxpdDaARWc--`，
   而 `用户B` 的原始文件 ACL 只有三条：
   `user:用户B:rwxp` / `group:users:--x` / `everyone:--x` ——
   **admin 读不到我们放进去的文件**（`cat` 直接 Permission denied，
   File Station 里也下载不了，症状和"文件坏了"一模一样）。
   查法：`synoacltool -get <文件>` 看有没有 administrators 条目。
   补法：

   ```bash
   synoacltool -add <文件> "group:administrators:allow:rwxpdDaARWc--:----"
   ```

   只对自己恢复出来的文件补，别去改用户原始文件的权限。

## 8. 踩过的坑

- **别用"能解压"当"能打开"**。1_可读内容 那批文件头是 0，zipfile 会报 BadZipFile，
  用户双击只看到"文件已损坏"。这是本次任务用户抱怨"一个都打不开"的根因之一。
- **别用宽松解析器判定文件好坏**。本次 29 个恢复件在宽松解析下全部"通过"，
  严格解析下**全部失败**（头部错位），结果用户报"无效文件格式"。宽松解析只能用来列条目。
- **同一批文件不要既放原名又放 `_部分修复`**，两份内容一样会让人以为恢复了两份。
  统一规则：全好→原名；部分→带后缀。
- **`0x26`（前 1MiB 加密）的文件，前 1MiB 全是推测值**，而容器头部正好在这 1MiB 里，
  所以头部必然要靠模板重建，不能靠推测。
- **逐字节盲扫 zlib** 会跑到天荒地老（22MB 文件里 729 个 zlib 头）。
  以条目名为锚点定点试，位置偏移量只有几十字节。
- **`.osheet` 是群晖上 WPS 用的表格格式**（WPS 表格的 OSheet 容器），直接在群晖里用
  WPS 打开；群晖的网页预览器不认识这个格式，在 File Station 里双击预览不一定会成功
  —— 别把"预览不出来"当成"文件坏了"。
  `.xlsx` 才是 Excel/WPS 通用格式，拷到电脑上双击就能开。两者是同一批数据的两份产物，
  按顺手用哪份都行。

## 9. 合并还原成 xlsx（"分片 CSV" 的正解）

上一轮抢救的产物是**每个工作表一个 CSV**（容器里 `text/sh_N` 一个工作表），
结果一个表格炸成十几个文件，工作表名字、顺序、样式全丢 —— 用户不认账，
说"那才叫还原修复"。

正解是用 `scripts/osheet_to_xlsx.py`（本地跑，依赖 openpyxl）把整个容器
还原成**一个 xlsx**：

```
python osheet_to_xlsx.py <输入.osheet> <输出.xlsx> [--csv <目录>]
```

要点（都已实现，别重写）：

- **工作表 = 标签页**：名字和顺序取自容器里的 `text/index`
  （`sheets` 里是 `sh_N → title`，`order` 是页序）。index 尾部常常多一个
  `\x00`，用 `json.loads` 会报 "Extra data"，必须用 `raw_decode` 取第一个对象。
- **样式表**在 `text/style` 条目里，结构是
  `{"styles":[[边框,字体,填充,数字格式,水平对齐,垂直对齐,?],...],
    "fonts":[{"n":字体,"sz":字号,"b":粗,"c":颜色}],
    "fills":[{"bg":"RRGGBB"}], "borders":[{"b":[左,右,上,下]}],
    "alignments":[{"h":..,"v":..,"w":wrap}], "numberFormats":[{"fc":"格式码"}]}`。
  **样式行第 1 位是字体、第 2 位是填充、第 3 位是数字格式、第 4/5 位是对齐。**
- **分片 JSON 可能被加密区截断**（`raw_decode` 报 "Expecting property name"）。
  按行抢救：逐个 `"行号":{...}` 用 `raw_decode` 解，能救多少救多少。
  实测 2321 行的分片能救回 2319 行。
- **日期**：单元格的数字格式是日期码时，序列号要换成真正的日期。
  但**只有 20000~2958465 的整数才算日期**（1、1.94 这种是小数，
  当日期会变成 1900 年）；原格式本来就是 `h:mm` 的格子保持原样。
- **超长整数**（16 位以上的订单号）Excel 存不下会丢精度 → 存成文本。
- **公式**：保留为公式（`wb.calculation.fullCalcOnLoad = True`，打开时自动重算）；
  公式里引用的格子如果没救回来，改成文本 `'=...`，免得算出个错数。
- **合并单元格**：被覆盖的格子里如果还有值，就不合并（否则丢数据）。
- 额外做的美化：表头行加粗 + 淡底色 + 冻结 + 自动筛选，列宽按内容自适应，
  批注还原，日期列统一 `yyyy-mm-dd`。

回读校验：抽样比对 xlsx 与源容器的每一格（日期比序列号、超长整数比文本）。

## 11. 容器打不开的四个坑（2026-10-31 实战，7 个文件全中）

上一轮"容器重建"把 `.osheet` 写坏了，用户报"打不开"。根因有四类，
**数据本身没坏**（每个分片的 JSON 都能解开），坏的只是容器框架：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 文件比原始长度多 11 字节 | 重建时在文件末尾**多追加了一段 11 字节的容器尾段**，原文件本来就有尾段，末尾变成两段 | 用勒索标记里的原始长度裁掉多出的 11 字节（`osheet_repair.py --orig-len=N`） |
| 2 | 末条目（附件条目）的 X 撑到几 MB | 重建时把 X 重算成"到尾部段起点"，于是把整个**附件数据区吞进了条目** | 附件条目的 X 只算条目本体（载荷 + 1 字节结束符），附件数据区放回条目链之外 |
| 3 | 头部解析直接失败 | 头部 `schema` 长度字段被推断成 **2**（正常是 3），头部整体错位一字节 | 把偏移 12 的长度字段改成 3（`prescan()` 自动做） |
| 4 | 条目链错位 / 末条目越界 | 加密区里推断出来的 X 字段本身是错的 | 按条目名锚点 + zlib 自终止重定位每个条目，X 按真实跨度重算 |

另外还撞到两种：

- **`id` / `ver` 两个字段的值写反**（合并步骤干的）：`id` 必须以 `b"<4位uid>_"` 开头，
  写反了就互换回来。
- **文件里嵌了第二份条目链**（开票登记表）：第二份正好落在被加密的区间里，
  字节不可靠（最后一个分片的 zlib 都解不开），整段丢弃。

### 已确认的容器文法

```
文件 := magic(4) + 头部TLV* + 条目* + [附件数据区] + [尾部段]
头部 := [u8 tag][key\0][值]      tag=0x08 用 u8 长度，其余用 u32 长度
       值后面若紧跟一个 0x00 是字段分隔字节（吃掉后继续解析下一个字段）
条目 := [u32 X][u8 tag][name\0][u32 len][tag==0x05 ? u8 0x00 : 无][payload(len)][尾随字节]
       X = 从 X 字段自身到本条目结束的总字节数
       尾随字节 = 载荷结束到下一个条目（或附件数据区）之间的原始字节
       @C_metatext 这类条目后面还会跟一段未压缩副本 [0x02][name\0][u32 len][raw]
尾部段 := [u32 总长][u8 0x08]["end\0"][值]      有的原件根本没有尾段
```

**附件数据区在条目链之外**：附件条目（`text/attachment` / `@C_text/attachment`）
的载荷是一段 JSON 元数据，紧接着 1 字节结束符，然后才是二进制附件数据，
附件数据区的开头是 `[u32 长度][0x03]["metabinairy_files\0"]...`。

### 条目名的两种形态（最容易踩的地方）

| 形态 | 名字 | 载荷 | 出现场合 |
|---|---|---|---|
| 压缩 | `@C_text/comment`、`@C_metatext` | zlib(len 字节) | **精确恢复出来的原件全是这一种** |
| 不压缩 | `text/comment`、`metatext` | 原始 JSON（带结尾 NUL） | 路由 A 候选件里全是这一种 |

⚠️ 裸名 `metatext` 会和 0x05 条目内嵌的未压缩副本撞名。
只有当它的 X 正好落在某个可信条目起点（或尾部段起点）上时，才算真条目；
认错了就会把它并进前一个条目的尾巴里 —— WPS 解析不了，整个文件打不开。

### 三个配套脚本

| 文件 | 作用 |
|---|---|
| `scripts/osheet_check.py` | **按上面这套文法做严格校验**（头部、条目链首尾相接、len 字段 == 实际载荷长、0x05 条目的 0x00 前缀与结束字节、附件数据区在链外、尾部段长度）。比 `osheet_strict.py` 严：它允许尾部有附件数据区，也认 0x02 未压缩条目 |
| `scripts/osheet_repair.py` | **容器修复器**：只重写头部与条目链的 X/len，其余字节逐字节保留；修 schema 长度字段、id/ver 写反、附件条目吞数据区、末尾多出的尾段。**必须先做往返验证**：`--selftest <正常件>` 要求输出与输入逐字节一致才可信 |
| `scripts/osheet_compress.py` | **不压缩 → 压缩形式改写**：把 0x02 条目压成 zlib、名字加上 `@C_` 前缀。WPS 可能只认压缩形式（实测"能打开"的那几个全是压缩形式），所以两种形式各出一份。对已经是压缩形式的文件跑，输出应与原件逐字节一致 |

```bash
# 往返验证（拿精确恢复的正常件）
python3 osheet_repair.py --selftest 客服上班表-最新.osheet 保税区退款订单.osheet
# 修复
python3 osheet_repair.py <坏件> <输出.osheet> --orig-len=22916716
# 压缩形式改写
python3 osheet_compress.py <文件> <输出.osheet>
```

## 12. "打不开"怎么分诊（2026-10-31 实战）

用户报"打不开"时，先看**报的是什么错**，两类完全不同：

| 报错 | 含义 | 怎么办 |
|---|---|---|
| "无法执行此操作，可能是因为网络连接不稳定或系统正忙" / 网络路径找不到 | WPS **没拿到文件内容**，不是格式错 | `.osheet` 要在**群晖上用 WPS 打开**（File Station 右键 → 用 WPS 打开）。在电脑上双击时 WPS 可能走云端转换，网络一抖就是这个提示。别急着改文件 |
| "无效文件格式" / "文件已损坏" | 容器结构问题 | 按第 11 节的四个坑逐条查 |

**顺带一个交付层的坑**：同一个文档在 home 里可能有好几份
（上一轮留下的坏件 + 这轮修好的 + xlsx），用户很容易点开错的那份。
**收尾时把每个文档只留一份恢复件、并统一用原始文件名**，
能省掉大量"我这边打不开"的来回。

## 13. 交付形态：.osheet 与 .xlsx 的分工

- **`.osheet`**：群晖上 WPS 用的表格格式（WPS 表格的 OSheet 容器）。
- **`.xlsx`**：Excel / WPS 通用格式，拷到电脑上双击就能开。
- 两者是**同一批数据的两份产物**：容器里的分片 JSON 用 `osheet_to_xlsx.py`
  还原成 xlsx（一个原表 = 一个工作簿，每个工作表一个标签页）。

**用户确认的口径（2026-10-31）**：表格类的正式交付物是**一个 xlsx**。
如果某个 `.osheet` 的容器实在修不好、怎么试都打不开，
**交 xlsx 就行 —— 用户可以自己在群晖里把它手动转成在线表格，不影响使用**。
不要因为一个打不开的 `.osheet` 死磕，更不要因为它不敢交 xlsx。

⚠️ **但 `.osheet` 里的附件（图片等）不在 xlsx 里**。
要用 `scripts/osheet_extract_attach.py` 把附件抠成普通图片另存一个目录，
再删 `.osheet`，否则附件数据会跟着文件一起丢
（实测一个表格内嵌 30 张照片、18 MB，抠出来逐张用 Pillow 验证过能解码）。
