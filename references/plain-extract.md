# 路线 B：提取未被加密的明文部分

## 为什么这条路存在

第一个案例（也是本 skill 的来源）教会我们一件事：**旧 extent 路线不是唯一的救法**。

某次真实恢复中，810 个被加密文件里有 650 个（80%）在 `survey` 里被判为 `no_candidate`——旧 extent 已被释放回收，看起来全完了。但实际检查发现：

- 这些文件的 extent 树里**只有一个 extent，且是攻击期新写的**（`gen` = 攻击代数），没有任何旧 extent 引用；
- 直接读块设备读那个 extent，全是 0（已被回收）；
- **但把新 extent 里的字节和勒索前的原件逐块比对，发现 88% 的字节与原件完全相同**。

原因很简单：勒索程序改写文件时，把**整个文件**写成了新的 extent。而它只对部分区间做加密，**未加密的区间写进去的仍然是原始明文**——只是搬到了新位置。

所以对于这类文件，不必找旧 extent，直接按加密模式切出明文区间即可。

## 加密模式怎么读

文件尾部 588 字节是 C3RB3R 追加的标记：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 48 | AES-256-CBC 包裹的密钥材料 |
| 48 | 520 | 其余密钥材料 |
| 568 | 4 | 会话标记（每次运行随机） |
| 572 | 1 | **模式** |
| 573 | 1 | **百分比参数** |
| 574 | 1 | 加密方式（0x20 = ChaCha8） |
| 575 | 1 | 保留 |
| 576 | 4 | 活动常量 |
| 580 | 8 | 原始长度 N（u64 LE） |

`c3r_btrfs.py` 的 `read_tail()` 已经会解析这些。模式取值与实测的加密区间：

### 0x24 —— 整文件加密

整个文件都是密文。**明文区为空，无路线 B 可言。**这类文件绝大多数小于 1MiB。

### 0x25 —— 分段加密（pct 常见 0x0a）

文件三等分，**每段的前 4% 被加密**，其余是明文：

```
w   = 4 * (n // 100)        # 每段加密长度，约占全文件 4%
gap = (n - 3 * w) // 2      # 段间明文间隙
密文区间 = [(0, w), (w+gap, 2w+gap), (2(w+gap), 3w+2gap)]
明文区间 = 约 88%
```

实证（用备份 zip 里的未加密原件逐 4K 块比对，n=16,374,950）：

```
第1段密文区 [0, 654996)          与原件相同 2510/654996 = 0.4%
第2段密文区 [7859977, 8514973)    与原件相同 2539/654996 = 0.4%
第3段密文区 [15719954, 16374950)  与原件相同 2524/654996 = 0.4%
```

0.4% 就是随机碰撞，正好说明这三段确实是纯密文，其余全是明文。

### 0x26 —— 前缀加密

只加密文件开头 **1MiB**：

```
密文区间 = [(0, min(n, 1<<20))]
明文区间 = [1MiB, n)
```

实测 256 个 4K 块全部落在 `[0, 1048576)`，一个不差。

> **注意**：`c3r_btrfs.py` 里的 `formula_ranges()` 已正确实现 0x24/0x25/0x26 三种模式，可直接复用其 `enc_ranges` 逻辑。不要自己另写一份公式——第一版手写时把 0x25 的百分比算成了 `4 * (n // 100)` 之外的量，结果整段判错。

### 未知模式怎么办

标记里的模式字节若不在 {0x24, 0x25, 0x26}，用 `scripts/probe_modes.py` 反推。原理是找**结构探针**：

- **zip 类**（xlsx/docx/zip）：中央目录在文件尾部，必定明文；每个成员的本地头 `PK\x03\x04` 偏移可从中央目录读出。扫全文件找这些偏移，若某区间内的成员头都能对上，说明该区间是明文。
- **PDF**：尾部 `%%EOF`（若存在则为明文）。
- **JPEG**：`FFD9`；**PNG**：`IEND`。

把这些探针的位置和"候选模型算出的明文区"求交集，就能确定真实边界。

## 提取方法

### 关键：保持原文件偏移

输出时**密文区填 0，明文区填原字节，文件总长不变**。这样：

- zip 的中央目录偏移依然正确，`zipfile` 能解析；
- PDF 的 xref 偏移依然正确；
- 后续的成员抢救可以基于正确的偏移进行。

如果把明文片段直接拼接（去掉密文区），偏移全乱，zip 就废了。

### 脚本

`scripts/plain_extract.py` 在 NAS 上跑，直接把结果写回目录：

```
python plain_extract.py <根目录1> [根目录2] ...
```

行为：
- 遍历目录下所有 `.L0CK3D`；
- 读标记、算加密区间、取明文区字节、密文区填 0；
- 写到 `<根目录>/勒索恢复_YYYYMMDD/1_可读内容/<原路径去掉.L0CK3D>`；
- **目标已存在则改名加 `.rN` 后缀，绝不覆盖**；
- 输出 `可读内容清单.json` 记录每个源文件的状态与明文占比。

### 抢救容器成员

填充后的 xlsx/docx/zip 仍可读出内部成员。`scripts/salvage_zip.py`：

- 从中央目录读出每个成员的**本地头偏移、压缩方法、CRC32、压缩后大小**；
- 本地头完整时按常规路径取数据；本地头落在密文区时，用中央目录的文件名长度 + 各种 extra 长度组合去定位数据起点；
- 解压后**用 CRC32 校验**，校验不过就丢弃这一成员；
- 输出到 `<用户>/勒索恢复_YYYYMMDD/2_抢救成员/<原路径>/<成员名>`。

实测一个 xlsx 救回 28 个成员中的 8 个，其中 `xl/worksheets/sheet2.xml` 有 2810 行、53390 个单元格，字段是「序号/发票代码/发票号码/销方识别号」——完整业务数据。

### 重建 PDF

PDF 不是 zip，但可以从明文区抽出对象体重建。**关键不在"抽出对象"，而在"有没有 Catalog"。**

PDF 阅读器打开文件时先找 `/Root` → Catalog → 页树。**没有 Catalog 的 PDF 一律拒绝打开**，
哪怕 `%PDF-` 头、`startxref`、`xref` 表、`%%EOF` 全都在（这种文件用脚本"看着正常"，实际双击就打不开）。

重建要点（`scripts/pdf_rebuild.py`）：

1. **保持原文件偏移**取明文区（密文区填 0），这样对象表里的偏移量才对得上。
2. 正则扫 `N 0 obj ... endobj` 收全部间接对象；顺带把 `/Type /ObjStm` 对象流解压，
   把里面的对象也放出来（PDF 1.5+ 大量对象在对象流里，不解会漏掉大半）。
3. 找 `/Type /Page`（注意别把 `/Pages` 也算进去）的页面对象。
4. **Catalog 处理**：
   - 有 `/Type /Catalog` 且它的 `/Pages` 指向的对象还在 → 直接用它当 `/Root`；
   - 没有 Catalog（或页树断了）→ **自己造一个**：新 Catalog + 新 `/Type /Pages`，
     `/Kids` 列出找到的页面对象，并把每个页面对象补上 `/Parent`。
5. 重排所有对象、重新生成 xref（`/Size` = 最大对象号+1，缺失的号补 `0000000000 65535 f`），
   trailer 写 `/Size` 和 `/Root`，最后 `startxref` + `%%EOF`。

**别把 `/Root` 写死成 `1 0 R`** —— 原文的 Catalog 往往不是对象 1，
或者压根不在明文区（`0x26` 的头 1MiB 是密文）。这是"重建出来但打不开"的头号原因。

交付前必须验：

| 检查 | 判据 |
|---|---|
| 结构 | `%PDF-` 开头；`startxref` 指向 `xref`；有 `/Root`；有 `/Type /Catalog` |
| xref | 逐条核对 xref 里的偏移量是否真的指向对应的 `N 0 obj`（错位=阅读器会判损坏） |
| 内容 | 每个页面的 `/Contents` 指向的对象**确实在文件里**（缺了就白页） |

实测：同一批文件，重建前 56 个 PDF 结构就是坏的（缺 Catalog），
修好后 45 个的内容流全齐、能正常显示。

## 验证（必须做，且必须区分"完整"与"部分"）

| 检查 | 判据 |
|---|---|
| zip 类 | `zipfile.ZipFile(p)` 能打开；成员能 `read()` 成功 |
| PDF | 以 `%PDF-` 开头；含 `%%EOF`；能数出 `/Type /Page` |
| 图片 | Pillow `Image.open()` + `load()` 不抛异常 |
| 明文占比 | `plain_bytes / orig`，**必须写进报告** |

**汇报口径**：`exact`（完整且经校验和证实）、`partial_plain`（明文部分，比例 X%）、`inferred`（推测）、`failed`（失败）——四类分开列，绝不能把"部分明文"说成"已恢复"。

## 实战数据（一次真实恢复的分布）

810 个加密文件的普查结果：

| mode | 数量 | 尾部明文 | 路线 B 能拿到 |
|---|---|---|---|
| 0x24 | 650 | 0% | 无（整文件加密） |
| 0x25 | 47 | 0% | 88% 明文 |
| 0x26 | 113 | 88% | 文件的绝大部分 |

最终落地：

- 路线 A（旧 extent）：20 个文件（6 精确 + 14 推测）
- 路线 B（明文部分）：160 个文件，1.25GB
- 路线 B + 容器抢救：155 个成员，31MB
- 路线 B + PDF 重建：59 个，233 页
- 路线 C（备份 zip 里的原件）：142 个完整原件
- **完全救不回**：650 个 0x24 小文件

## 什么情况下这条路无效

- 模式是 0x24（整文件加密）→ 无明文可取。
- 文件是 0x25/0x26，但**内容本身是压缩流**（xlsx 的 sheet 数据、zip 内的文档）→ 密文区填 0 后无法解压，只能靠中央目录 + CRC 逐成员抢救。
- 图片类：头部（IHDR/SOF）在密文区时无法解码，只能拿到明文片段。

## 找原件（路线 C）优先于一切

在写代码抢救之前，**先确认用户手上有没有备份**。真实案例里，最终 142 个完整原件（142/142 SHA 逐个复核通过）全部来自一个 7.9GB 的自备份 zip——它比任何算法抢救都干净。

查找顺序：

1. **自备份 zip**：勒索程序改名前的目录快照。里面既有加密后的条目（`.L0CK3D`），也有当时**没被加密**的条目。
2. **同名同大小比对**：zip 里的未加密条目与当前的密文文件，`basename` 相同且**大小差正好 588 字节**（标记长度）→ 极可能就是原件。逐字节比对确认。
3. **zip 里的 `.L0CK3D` 条目与当前目录的加密文件**：相对路径 + 大小都相同 → 说明 zip 就是加密后的快照，可以用它的中央目录辅助分析。
4. **回收站 `#recycle`**、同步盘、NAS 快照目录。
5. 其它用户目录、手机、云盘、邮件。

> **同名不等于同一份文件**。`1.png` 这类通用名在 zip 里可能对应完全不同的图片。只有逐字节比对一致才能认定为原件。
